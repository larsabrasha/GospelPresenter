# The native apps: SwiftUI over the Rust core

Lars, 2026-11-17: the native iOS app is built now, SwiftUI over the Rust core (`crates/gp-core`), beside the Capacitor
shell in `apps/mobile` (docs/phone-app.md). The Mac app is the same SwiftUI in `apps/mac`, one code for both where it
can be; the core is the web's, so a native app shows what the web shows and syncs by the web's rules
(docs/rust-core.md). Android comes later, through the same interface in Kotlin.

## The core's interface: UniFFI

`crates/gp-core-ffi` is the core for native shells (plan item 4 of docs/rust-core.md): Swift types and functions
generated by UniFFI (Mozilla's) from the Rust ones, instead of the hand-written C interface with JSON it replaces. The
web keeps JSON over WASM (`crates/gp-core/src/bridge.rs`'s C functions); both doors lead to the same steps.

- `start(name, args, caller)` begins a command or a view; `resume(answer)` gives the rows of the statement it asked
  for. Each answers a `Step`: `done` (a view's JSON text, none for a command), `refused` (the code), or `sql` (a
  statement and its parameters). The core still never opens a database: the shell runs every statement (an effect).
- `SqlValue` is SQLite's null, integer, real or text, both ways; `SqlAnswer` is the rows, or SQLite's refusal, which
  fails the command as `sql-error`. A blob is answered as null (the core reads no bytes). A whole real reaches the core
  as an integer and a whole number is bound as one, as JavaScript's numbers do on the web, so both give the core the
  same values (`crates/gp-core-ffi/src/lib.rs`'s tests).
- `Caller` is the user, the role and, where the server decides, its clock.
- What stays JSON text: a command's arguments and a view's answer, which the core reads and writes as JSON for the web
  too. The Swift side decodes a view's answer into its own `Decodable` types (`apps/mac/Sources/GPMac/Views.swift`);
  typed views would need each view's answer as a Rust type, a change to every view not made.
- A call waits in its thread's own state between its steps, so every call comes from one thread: the Swift `Core` is on
  the main actor, so the compiler holds every call there.

The bindings are generated by `crates/gp-core-ffi/bindings.sh` from a debug build's metadata, into
`apps/mac/Sources/Shell/CoreBindings.swift` and `apps/mac/Sources/GPCoreFFI/gp_core_ffi.h`, which git ignores: the
build scripts make them before Swift builds. UniFFI is pinned (0.32.2); its `cargo-platform` is held at 0.3.2 in
`Cargo.lock`, the last that builds with the Rust here (1.90).

## Building, running and installing

```sh
apps/mac/apple.sh                      # the core for macOS, iOS and the simulator as build/GPCore.xcframework, the bindings, the texts, the slide renderer, the demo data
apps/mac/apple.sh ios                  # that, then the iOS app for the simulator
apps/mac/apple.sh run "iPhone 17 Pro"  # that, installed fresh and started in that simulator
apps/mac/apple.sh device               # the iOS app for a device, unsigned: proves it compiles and links
TEAM=<team id> apps/mac/apple.sh install <UDID>   # signed with one's own team, installed and started on a device
crates/gp-core/build.sh run            # the Mac app on a fresh copy of the demo data
```

The Xcode project (`apps/mac/ios/GPiOS.xcodeproj`) compiles `apps/mac/Sources/GPMac` as a synchronized folder and takes
the `Shell` library from the Swift package, so a new Swift file needs no project edit. `apps/mac/ios/Info.plist` adds
what the generated plist cannot: plain http on the local network (`NSAllowsLocalNetworking`) and the local network's
purpose text. The simulator does not take text pasted from the Mac; a launch argument fills the address field
(`xcrun simctl launch <device> com.gospelpresenter.native -gp.lastServer 127.0.0.1:47843`).

## Signing in and syncing

The app connects to a church's desktop host (docs/sign-in-and-pairing.md, pairing): its address, then the six-digit
code from Enheter → Anslut enhet, or no code on a host started with `GP_DEV_PAIR=1`. The session and the device's
token are kept in the Keychain, so the app opens straight into the organisation's database, one file per organisation
(`org-<id>.sqlite`), with no network. Signing in to the cloud (Google, passkeys) is not built.

A host started with `GP_TLS=self-signed` has a certificate no device trusts. The app shows its SHA-256 once, the person
compares it with the host's and accepts it, and from then on only that certificate is accepted for that address, as a
browser's warning is accepted once (`PinnedCertificates` in `apps/mac/Sources/Shell/Server.swift`). Plain http works on
the LAN too.

Sync is the core's, the web's too (Lars, 2026-11-20): the queue and the rebase (`syncMutate`, `syncRebase`), and the
driver `syncStepView` (`crates/gp-core/src/sync_driver.rs`, `sync_wire.rs`), which decides when to sync, builds each
request, reads each answer and says what to do next. `apps/mac/Sources/Shell/Sync.swift` only does what it says, as
`packages/sync/src/client/client.ts` does on the web:

- opening: `PRAGMA foreign_keys = ON`, then `migrateOrgSchema` and `syncOpen` in one transaction;
- a change: `syncMutate` in a transaction of its own, then a sync, as the web's worker does after every change;
- the driver's effects: a request to post (its body JSON's text, each change's arguments as the core queued them), a
  page to keep, the rebase (`syncRebase` over the pages kept, in one transaction; its refusals kept, the pages read
  again when it changed rows), the poke socket to open or close, a timer, the media to fetch (`onMedia`);
- the events the shell sends back: the answer's status and text, a failed request, the rebase done, the socket opened,
  a poke, the socket closed, a timer run out;
- what the driver holds to: a sync on every poke and every connection, a new try 3 s after the socket closes, a poll
  every 5 minutes, runs coalesced to one running and one waiting; "update required" (426) and refused credentials
  (401/403) stop syncing and keep the queue, and the account menu says so. Signing in again is by connecting again
  (Logga ut first).
- The socket closes when the app goes to the background (`close`) and opens again, with a sync, when it comes back.

Checked against a real server by `apps/mac`'s `parity sync` (`apps/server/test/native-sync.test.ts`, run by
`crates/gp-core/build.sh test`): two devices see each other's changes through pokes, the queue empties, refused
credentials stop syncing with the queue kept, and closing closes the socket.

Tried against a desktop host on this Mac, from the iPhone 17 Pro simulator (2026-11-17), with the host's commands:

```sh
GP_LAN=1 GP_TLS=self-signed GP_DEV_PAIR=1 GP_PASSKEY_RP_ID=localhost GP_PASSKEY_ORIGINS=http://localhost:8787 pnpm --filter @gp/desktop serve
```

(passkeys only so setup can finish without Google; setup itself is the host window's, or `POST /api/auth/setup` with
the host token). The host's certificate was accepted once; a presentation made on the iPhone showed on the web at the
host's address (the browser paired as a second device), and one made on the web showed on the iPhone within a second,
through the poke. Not tried: a real iPhone on the LAN, offline changes rebased on a real network, a refused change, a
role change, an organisation with thousands of songs.

## The pages and the way between them

The structure is the web's (Lars, 2026-11-17): `docs/layout-2-0.md` describes it, and where the file and the running
web app differ, the web app wins. Built with SwiftUI's own components shaped to it, not a copy of the web's CSS:

- **Windows** (`AppState.swift`, `Model.swift`): the app holds its data, sync, start page lists and live state once
  (`AppState`); each window, an iPad's or a Mac's, has its own `Model` over it (`InWindow` in `GPMacApp.swift`): its
  way through the pages and its page's own state, so two windows select and make ready on their own and see the same
  presentation presented. A change of the data made in one is read again in all; a step into another item moves only
  the selection of the window that stepped (docs/layout-2-0.md). A presentation has one window: opening one another
  window has open brings that window forward (`Model.path`, `bringForward`), and the Mac's output window sends its
  keys there.

- **The start page** (`apps/mac/Sources/GPMac/StartPage.swift`) is a list of its own at every width: what this device
  presents at the top ("Visas just nu"), then Idag, Kommande and Senast ändrade (20 at a time, Visa fler), each row
  two lines with its number of items; the round blue + in the bar makes a presentation ("Skapa presentation", then it
  opens); the user's picture holds the name, the sync's state only while it has a problem (Synka nu) and Logga ut.
- **A presentation** opened from it is pushed on the same `NavigationStack`, with ‹ back; presenting goes on when one
  goes back (`Live.swift`). Its bar: the title and under it when and where (LIVE first while presented); a tap on the
  title opens the presentation's menu (Redigera detaljer…, Noter och länkar (`presentationMaterialsView`, a sheet), Radera presentation when not presented, asked first); ▶ or
  ■ at the far right, ■ asking first. From about 1 000 pt wide (`WideLayout.swift`: a computer, an iPad lying down, a
  13-inch iPad upright) the running order at the left with the description card at its top, the slides of every item
  in the middle (sections with sticky headings, tiles 384 shrinking to 340 pt), and while presenting the live column
  at the right (the picture, Släck, the next slide); each side folds away. Narrower (`PhoneLayout.swift`), one column:
  while presenting the picture small at the left with Släck at its right and under Släck, as the web's, Beskrivning
  (a sheet with the description and Redigera detaljer) and Visning (a sheet with a switch for each overlay; no outputs
  on iOS yet), then every part a row with its whole text, VISAS and NÄSTA on them, + floating at the bottom right. The
  overlay turned on lies over the live picture and the Mac's output window, none while black (`Live.overlay`). The slide shown and the one made ready are marked as each
  platform marks a choice (Lars, 2026-11-18): a row by its ground, faint red or faint blue, with no lines to its
  neighbours, as a list's selection is on iOS; a tile by a ring inside its edge. The marking is the app's own, not
  `List(selection:)`: a list's selection is one kind in the system's colour, does not answer a tap on the row already
  chosen (after Släck that tap shows it again) and moves itself with the arrows, which are the core's.
- **An item's menu** (`ItemMenus.swift`), the same on its row and its heading's …: Byt namn for a programme item,
  Kommentar; Arrangemang ›, Överlägg › (Ingen or one of the organisation's, `setItemOverlay`); Lägg till efter ›; Redigera (where the core's `opens` says: the song's page, the slideshow's editor, the item's pictures, in a sheet;
  ItemEditing.swift); Markera (select mode, `tickView`: in columns the running order ticks in place, on a phone a sheet of it; the ticked removed together after a question; Ticking.swift); Radera last, in red, asked first, and
  disabled for the item on the outputs, black or not. **+** offers Sång, then under a line Programpunkt.
  `apps/mac/apple.sh uitest` checks these menus against the core's answers for a scenario (docs/view-models.md).
- **Colours and sizes** (`Look.swift`): the warm grey `stone` by role (ground, surface, raised, sidebar), sky-500 as
  the app's tint, rows at least 52 pt.
- **Texts** are the web's own, Swedish and English: `apps/mac/texts.mjs` writes `apps/web/src/i18n.ts`'s table into a
  Swift file (not kept in git) at every build, and `t("presentations.today")` reads it in the device's language
  (Swedish when it is neither). The few the web has no use for (the host's address and certificate, the demo) are in
  `Texts.swift`, as i18n.ts may hold only keys the web's code uses.

## Slides: the web's SlideView in a web view

Lars, 2026-11-17: slides are drawn by the web's own code, the rest of the app is native. A slide on the iPad must look
exactly as on the projector, and every output (the output window, paired screens, `/display`, `/watch`) is the web's
`apps/web/src/ui/SlideView.tsx`: a 1920×1080 stage scaled to fit, its text fitted by measuring it in the browser
(`FittedText`), themes and their fonts, Bible verse numbers, custom pages, pictures. A second renderer in SwiftUI would
drift from it; the prototype's `SlideFace` (the default theme only, its font size guessed from the characters) is gone.

- **The renderer** is a page of its own in the web app, `apps/web/slides.html` with `apps/web/src/slides/main.tsx`,
  built by `apps/web/vite.slides.config.ts` (relative addresses, not part of the web app's build) and copied into the
  app by `apple.sh`. It offers two calls: `gpSheet` draws a grid of tiles, `gpShow` one slide filling the view. Swift
  feeds them the core's own JSON: the slide, the presentation's theme, the item's overlay.
- **No network**: the app serves the renderer's files and the pictures itself through the `gp:` scheme
  (`AppScheme` in `apps/mac/Sources/GPMac/SlideRenderer.swift`): `gp://app/…` from the app, `gp://media/{hash}` from
  the device's own storage.
- **The live picture** (and the Mac's output window) is a web view of its own, drawn as an output draws (no label,
  with the credits).
- **Thumbnails** (`Thumbnails.swift`, Lars, 2026-11-17): one hidden web view lays out up to 20 slides as a grid, one
  snapshot is taken, and the tiles are cut out in Swift, at 480×270 pixels. Kept by content, not by presentation: the
  key is a hash of the slide, the whole theme, the size and the renderer bundled (its page names its scripts by their
  hash), so an edited theme or a new renderer is new keys and nothing is cleared by hand. On disk in Caches (the
  system may empty it; then slides are drawn again), at most about 100 MB, the least recently used going first; in
  memory above it. An overlay is a layer of its own, drawn once on a clear ground and laid over the slide's picture,
  as the web's `OverlayLayer` lies over the slide: a snapshot keeps the clear ground (checked: the corner's alpha is
  0). The tiles on screen ask first, the rest of the presentation is fetched after them; while one waits, the theme's
  background colour holds its place.
- **Slides painted** (Lars, 2026-11-19; way 3 of `docs/native-slide-rendering.md`), on the Mac and iOS:
  `SlidePainter.swift` and `SlideItems.swift` paint every kind (song, Bible, picture, a video's still, a slideshow's
  page, an overlay over any) from the core's `slideLayoutView` with Core Text and Core Graphics, in thumbnails and in
  the live picture and output window (a SwiftUI `Canvas`); the web view only where the core refuses (a face it lacks)
  or this cannot read a colour. `GP_PAINTER=0` draws all with SlideView; the
  check against SlideView is `apps/mac/compare.mjs` (`-gp.compare YES` in the simulator).
- **Audio and video live** (Lars, 2026-11-19; `LivePlayer.swift`, `LiveMedia.swift`): the device presenting plays
  them as the web's Player does (docs/live.md "Where audio and video play"): a video or audio item shown plays from
  its start, anything else shown stops it, Släck pauses it and a slide shown again plays it on where it was, unless it
  was paused by hand, each step as the core works it out (`playbackStepView`, below) and the player does; the next
  item's video is fetched meanwhile. One AVPlayer, so the sound plays once and every
  live picture of the device (the window's, the Mac's output window) shows the video between the slide's still and
  the overlay. Under the live picture: play or pause, the position, the time, and an audio file's Tona ut (5 s,
  easing out, then paused at the start). The files come from the host by their hash (`GET /api/media/{hash}`, the
  shell's `SyncClient.media`) into the media folder, whole before they play; with the demo, only what lies there.
  Checked by `GP_MAC_PLAYTEST=<file>` (`PlayTest.swift`, muted) with test files under the demo's hashes: each rule
  above as the player's state says it. Not checked: a file fetched from a real host, the picture on a screen, iOS,
  and AirPlay. A video is fetched whole before it plays, where the web streams it (its play token); not yet the web's.
- **Media files** (Lars, 2026-11-19, the core's plan since 2026-11-20; `MediaSync.swift`): the core's `mediaPlanView`
  is given the media folder's files ({hash, size, at}) and says what to fetch (every picture's and video's thumbnail,
  themes', slideshows' and overlays' pictures, and while presenting the presentation's full pictures, audio, stills
  and pages) and what to remove (what nothing names past the hour's grace, never what a queued change names, and the
  oldest of what nothing wants now while that is over the 2 GiB budget; never the videos the player has, `inUse`, nor
  while presenting the presentation's videos), as the web's syncMedia; fetched after every
  sync and when presenting starts or ends, each file's SHA-256 checked before it is kept (`Server.download`); what
  arrives draws the tiles with pictures again (`TileRequest.media`). Checked against a real server by `parity sync`
  (a file fetched is the one uploaded, one the server lacks is not kept). Uploads (2026-11-21): a file imported
  (Inställningar's pictures, sounds, a song's notes) is kept in the media folder by its hash and recorded in
  `media_blobs` with a one-byte mark for its bytes (the core reads none; `mediaUploadsView` asks `bytes IS NOT NULL`),
  and before a push `SyncClient.uploadBeforePush` sends what `mediaUploadsView` and `bibleUploadsView` list
  (`PUT /api/media/{hash}`, `PUT /api/bibles/{hash}`), as the web's uploads do: the first that gets no answer or a
  5xx is the push's limit; a refused one (4xx) or a file not here is not sent again that push. Checked against a real
  server by apps/server/test/native-settings.test.ts. Not done: presentations kept offline but by hand (Lagring), a refused Bible import queued again.
- **Bible texts** (Lars, 2026-11-21; `Shell/BibleTexts.swift`, `BibleSync.swift`): as the web's syncBibleTexts, the
  core's `bibleTextPlanView` says which texts to drop and fetch (those of the translations kept, `kept_bibles`) and
  `bibleTextStoreView` whether one fetched is what its hash names, and how it is kept; after every change and pull.
  `keepBible` keeps a translation and fetches its text now, or drops it. Checked against a real server by `parity
  sync` (an import reaches the other device, its text fetched only once kept, dropped when no longer kept, a text
  not what its hash names not kept). Not done: anything that shows them; the app has no sheet to add a reading
  yet, nor a way to choose a translation to keep, nor imports of its own.
- **Rows and previews as the web's** (`ItemPreview.swift`, `PhoneLayout.swift`): on a phone a picture, a video and a
  slideshow's page show small in their row, an audio file's with its speaker and its name beside (the web's SlideRow
  and AudioMark), a song's or reading's part by its words or number; a tile of an audio item has the speaker and the
  name. Before presenting, an audio item has its name and its own player (Tona ut too), a video item its still with
  the system's player, each fetching its file when first wanted (the web's ItemMedia).
- **Measured** in the iPhone 17 Pro simulator on this Mac (2026-11-17, `-gp.demo YES -gp.measure YES`, Swedish song
  slides in the classic theme): one snapshot 65 ms, a sheet of 20 69 ms, 100 slides cold (caches emptied) 1 140 ms,
  from disk 37 ms, from memory 14 ms. Not yet measured on Lars's iPhone: the simulator runs on the Mac's processor,
  so the phone's numbers will differ. The cold 100 is more than five sheets because the tiles come in smaller
  batches than 20 as they are asked for; not tuned.

Launch arguments for pictures and checks: `-gp.demo YES` opens the demo data, `-gp.open <presentation id>` a
presentation, `-gp.show <item id>/<n>` presents that slide, `-gp.measure YES` writes the numbers above to the log and
to the app's `Caches/measure.txt`. For example
`xcrun simctl launch <device> com.gospelpresenter.native -gp.demo YES -gp.open pres-main -gp.show pres-main-i1/1`.

The core's older views that only the prototype read (`presentationsView`, `presentationView`, `trashView`,
`liveView`) are no longer read by the app; they are still in the core.
